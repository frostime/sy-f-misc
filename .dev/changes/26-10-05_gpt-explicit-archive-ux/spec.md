# 显式归档与两步残留清理

## 用户目标

临时工作版与永久存档是两份副本。复制链接、导出、备份、清理不应暗中连带覆盖永久存档；用户必须知道写什么、写到哪里以及哪些数据仍未归档。

## 边界

- 归档以明确用户确认写当前操作开始时的完整工作快照。首次建立与覆盖更新区分；确认展示准确文件路径、两侧全部存储节点/版本数量，不渲染原存档全文。数量不是内容 diff。
- 文件读失败不当作不存在；确认期间永久正文变化则中止重试。保留旧工作版覆盖新存档的警告，但只弹一次归档确认；不宣称跨设备原子 CAS。
- 复制链接仅对现有可读取永久存档生成链接，不创建文件。链接指向可更新的存档，不是不可变版本，也不包含未归档工作变化。
- 导出只更新对应笔记/附件目标，不附带永久 JSON 保存。删除原先“导出但不归档”的特殊分支与混合 persistHistory 入口。
- 残留预览仅预留备份 ID，展示新增永久历史文件；用户明确保存备份后读回核验全部数据，当前工作版不改变。返回/取消不删除已创建的备份。
- 单独清理需要宿主私有凭据，且来源快照与备份仍完整匹配；后台重读后再次检查会话/生成状态，任何变化拒绝。只改工作缓存；原永久存档更新必须另行确认。
- JSON 写失败须传播，索引不发布假成功。正文已写入但索引失败明确报告部分完成，清理不取得备份凭据。保留数据，不自动删除失败操作留下的文件。

## 非目标

不修改 JSON schema、ID 规则、缓存生命周期，不自动清洗旧存档，不添加永久版本库、全量差异系统或跨设备事务。没有实际部署或清理用户历史。

## 文件责任

- persistence/archive-actions.ts：建立/覆盖确认、取消、只读复制链接。
- persistence/json-files.ts：实际文件存在/失败状态、写入失败传播、独立文件创建保护及正文成功后索引更新。
- persistence/history-equality.ts：比较完整 JSON 持久化快照，忽略对象 key 顺序，不忽略数组顺序/字段。
- persistence/index.ts：导出不归档；直接导出 archive/link 意图接口。
- residue-cleanup.ts：明确备份阶段、完整读回核验、明确清理阶段、来源/备份再检查与本地失败恢复。
- residue-review/index.ts：备份候选与核验凭据宿主私有持有，SDK 不接收 iframe 自造凭据。
- residue-review/chat-tree-residue.html：两按钮两步骤、文件位置、取消保留、清理后可选归档。
- main.tsx / HistoryList.tsx：入口接入；批量归档逐项确认，取消/失败停止且未处理项仍勾选，不误报整体成功或删除缓存。
