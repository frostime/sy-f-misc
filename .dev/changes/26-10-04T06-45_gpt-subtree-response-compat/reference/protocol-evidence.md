# Protocol Response Compatibility — Upstream Evidence

Bounded research on the three in-scope protocols (OpenAI-compatible Chat Completions, Claude Messages, Gemini generateContent), performed by reading official SDK sources via GitHub API (`gh api`), plus the OpenRouter docs page for `reasoning_details`. No secrets or settings were read.

## 1. OpenAI Chat Completions — openai/openai-node

- URL (inspected, `main` branch):
  - `src/resources/completions.ts` — https://github.com/openai/openai-node/blob/main/src/resources/completions.ts
  - `src/resources/chat/completions/completions.ts` — https://github.com/openai/openai-node/blob/main/src/resources/chat/completions/completions.ts

Semantics confirmed from source:

- `CompletionUsage` (completions.ts L132–157): `completion_tokens`, `prompt_tokens`, `total_tokens` (required numbers), plus `prompt_tokens_details` and `completion_tokens_details`.
- `CompletionUsage.PromptTokensDetails`: `audio_tokens`, `cache_write_tokens` ("The unadjusted number of prompt tokens written to cache"), `cached_tokens` ("Cached tokens present in the prompt"), `image_tokens`, `text_tokens`. **`cached_tokens` is a subset of `prompt_tokens`.**
- `CompletionUsage.CompletionTokensDetails`: `accepted_prediction_tokens`, `audio_tokens`, `reasoning_tokens` ("Tokens generated by the model for reasoning"), `rejected_prediction_tokens`, `text_tokens`. Reasoning tokens are included in `completion_tokens` (billed as output).
- Streaming (`ChatCompletionChunk`, chat/completions/completions.ts L1028–1113): `usage` is present with a **null value on every chunk except the last**, which carries the full usage — only when `stream_options: {"include_usage": true}` is sent. The last chunk's `choices` array **may be empty**. If the stream is interrupted, the final usage chunk may never arrive.
- `reasoning_content` / `reasoning` / `reasoning_details` are **not** official Chat Completions fields in openai-node types; they are provider extensions (DeepSeek-style `reasoning_content`, OpenRouter `reasoning`/`reasoning_details`). Our adapter therefore parses them defensively.

## 2. Claude Messages — anthropics/anthropic-sdk-typescript

- URL (inspected, `main` branch): `src/resources/messages/messages.ts` — https://github.com/anthropics/anthropic-sdk-typescript/blob/main/src/resources/messages/messages.ts

Semantics confirmed from source:

- `Usage` (L3905–3946): `input_tokens` (number), `output_tokens` (number), `cache_creation_input_tokens` (number|null), `cache_read_input_tokens` (number|null), `cache_creation: {ephemeral_5m_input_tokens, ephemeral_1h_input_tokens}`, `output_tokens_details: {thinking_tokens}`.
- **Additive cache semantics** (documented on the usage field, L2636–2637 and L2866–2867): "Total input tokens in a request is the summation of `input_tokens`, `cache_creation_input_tokens`, and `cache_read_input_tokens`." I.e. unlike OpenAI/Gemini, Claude's cache counts are NOT subsets of `input_tokens`.
- `output_tokens_details.thinking_tokens`: "Number of output tokens the model generated as internal reasoning, including the thinking-block delimiter tokens… Always ≤ `output_tokens`" — i.e. a subset of output_tokens, unlike Gemini's `thoughts_token_count` which is excluded from `candidates_token_count`.
- `MessageDeltaUsage` (streaming `message_delta`): cumulative `input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`, `output_tokens_details`.
- Streaming deltas (`ContentBlockDeltaEvent.delta`): union of `TextDelta`, `InputJSONDelta`, `ThinkingDelta` (delta.thinking, concatenated across events), `SignatureDelta` (delta.signature — opaque, not displayable content).
- `RedactedThinkingBlock` (L2912–2928): `data` field "opaque and encrypted, with no readable content" — must not be shown or stringified as text.
- Non-streaming `content` blocks: `text`, `thinking` (thinking text + `signature`), `tool_use`, `redacted_thinking`.

## 3. Gemini generateContent — googleapis/js-genai

- URL (inspected, `main` branch): `src/types.ts` — https://github.com/googleapis/js-genai/blob/main/src/types.ts

Semantics confirmed from source:

- `GenerateContentResponseUsageMetadata` (L3741–3757):
  - `promptTokenCount`: "includes any text, images, or other media… When `cached_content` is set, this also includes the number of tokens in the cached content" → `cachedContentTokenCount` is a **subset** of `promptTokenCount`.
  - `candidatesTokenCount`: total tokens in generated candidates — **excludes** thoughts.
  - `thoughtsTokenCount`: tokens of the model's generated "thoughts" output.
  - `totalTokenCount`: "the sum of `prompt_token_count`, `candidates_token_count`, `tool_use_prompt_token_count`, and `thoughts_token_count`" → **total includes reasoning not reflected in `candidatesTokenCount`**.
  - Also `toolUsePromptTokenCount`, `cacheTokensDetails` / `candidatesTokensDetails` / `promptTokensDetails` (modality breakdown arrays — kept out of the normalized `ICompletionUsage`, raw kept in `providerMeta`).
- `Part` (L2140–2160): `thought?: boolean` — "Indicates whether the `part` represents the model's thought process or reasoning"; `thoughtSignature?: string` — "opaque signature… base64" (ignore for display). Thought parts carry their text in the normal `text` field, so parsing must check `part.thought === true` to separate reasoning from answer.

## 4. OpenRouter `reasoning_details` — OpenRouter docs

- URL (inspected; redirects to canonical): https://openrouter.ai/docs/use-cases/reasoning-tokens → https://openrouter.ai/docs/guides/best-practices/reasoning-tokens

Semantics confirmed from the page:

- Plain-text reasoning: `message.reasoning` (string); `reasoning_content` is documented as an alias "functionally identical".
- Structured: `reasoning_details` array. Location: `choices[].message.reasoning_details` (non-streaming) and `choices[].delta.reasoning_details` (streaming, "complete reasoning sequence is built by concatenating all chunks in order").
- Detail types (three): `reasoning.summary` (`summary` field), `reasoning.text` (`text` field + optional `signature`), `reasoning.encrypted` (`data` field, opaque/encrypted). Legacy short forms `text` / `summary` / `encrypted` also circulate in the ecosystem.
- Common fields on each detail: `id` (string|null), `format` (e.g. `anthropic-claude-v1`, `google-gemini-v1`), `index` (number, optional).
- Usage: page confirms `usage.completion_tokens_details.reasoning_tokens` exists in Chat-Completions-compatible usage.
- "For encrypted reasoning, the content may appear as `[REDACTED]` in streaming responses" — encrypted details carry no displayable text and must be skipped, not stringified.

## 5. DeepSeek Chat Completions cache counters

- URL (inspected): https://api-docs.deepseek.com/api/create-chat-completion/

Semantics confirmed from the official response schema and examples:

- Top-level usage fields `prompt_cache_hit_tokens` (integer) and `prompt_cache_miss_tokens` (integer), with the documented identity `prompt_tokens = prompt_cache_hit_tokens + prompt_cache_miss_tokens`.
- `prompt_tokens_details.cached_tokens` is documented as "Same as `prompt_cache_hit_tokens`" (example: `cached_tokens: 0`, hit `0`, miss `16`, prompt `16`).
- Streaming usage final chunk carries both counters (example: hit `0`, miss `17`).

Mapping: `prompt_cache_hit_tokens` fills `prompt_tokens_details.cached_tokens` only when `cached_tokens` is unreported (DeepSeek itself always supplies the equal `cached_tokens`); the actual miss count is preserved as `prompt_tokens_details.uncached_tokens`. No other vendor aliases were mapped.

## Mapping decisions (this implementation)

| Protocol | prompt_tokens | completion_tokens | cache read | cache write | reasoning tokens | total |
|---|---|---|---|---|---|---|
| OpenAI | `prompt_tokens` | `completion_tokens` | `prompt_tokens_details.cached_tokens`, with DeepSeek hit alias fallback (**subset**) | `cache_write_tokens` → `prompt_tokens_details.cache_creation_tokens`, raw alias retained | `completion_tokens_details.reasoning_tokens` (**subset**) | as supplied |
| Claude | `input_tokens` + reported cache reads + writes | `output_tokens` | `cache_read_input_tokens` → `prompt_tokens_details.cached_tokens` (**subset after folding**) | `cache_creation_input_tokens` → `prompt_tokens_details.cache_creation_tokens` (**subset after folding**) | `output_tokens_details.thinking_tokens` → `reasoning_tokens` (**subset**) | inferred only when normalized input and output are both known |
| Gemini | `promptTokenCount` + `toolUsePromptTokenCount` | `candidatesTokenCount` + `thoughtsTokenCount` | `cachedContentTokenCount` (**subset**) | — | `thoughtsTokenCount` → `reasoning_tokens` (**subset after folding**) | as supplied; else input + output when both are known |

- Raw provider usage is available in the adapter result under `providerMeta` (`claudeUsage` / `geminiUsage`). Chat versions persist/display the normalized usage, not these raw response objects.
- Missing basic counts stay `undefined`; no total is inferred from just one side. Reported details and explicit zeros are retained even when their parent basic count is unknown.
- Optional additive cache/thought/tool-use components absent from their native protocol contribute no additional count when the corresponding base count is reported; absence does not create a displayed zero detail.
