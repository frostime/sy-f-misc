# 三协议通信修复目标

用户要求检查 OpenAI-compatible Chat Completions、Claude Messages、Gemini generateContent 的基础通信，并授权直接修复证据充分、行为明确的问题；有实质选择时先讨论。原始检查见同目录 `protocol-compat.AUDIT.md`。

## 本轮直接修复

- 请求和解析使用同一个最终流式模式；模型能力与参数开关不能被外层 stream 值绕过。
- HTTP 错误、已识别的流内错误、错误响应结构和提前 EOF 返回明确失败，保留已经收到的正文与 usage。
- 工具链不能把模型请求失败记为正常完成，也不能继续执行失败响应中的工具；协议返回的错误要清楚可见。
- OpenAI 工具参数分片即使每片携带 id，也按同一个调用正确合并。
- 标准拒绝回答和已知 Gemini 安全拦截原因不再静默消失。
- Claude 手动 thinking 的预算与输出上限矛盾时，在发请求前给出明确错误，不擅自提高用户的输出预算。
- Claude 工具 input_schema 不再静默丢掉根部 JSON Schema 约束。

测试应使用生产适配器/解析器/工具链，仅替换模型网络与宿主边界。普通文字、图片、工具、流式进度和既有历史版本归属保持不变。不增加自动重试、回滚、Provider 猜测或新的原生 API。

## 协议回传数据（用户已建议采用 extra）

- 内部消息与 completion 使用 `extra` 承载原生协议必须回传的数据；不能只保留可读推理而丢签名/加密内容。
- 数据经过流式/非流式解析、工具续轮、回答版本保存及 JSON 重载后仍可用于同来源请求。`extra` 本身不直接发给 API，也不混进展示正文。
- 不把某协议、模型或 provider 的原始数据盲目发给另一来源。旧记录缺少 extra 时保持可读取，不伪造丢失的签名。
- 用户编辑协议消息时，适配器不能用旧原始块覆盖编辑后的正文。旧回答版本仍保留其对应的数据。
- Gemini 工具调用不能因 chunk 局部下标相同而丢失；服务端 id 与结果正确关联，复杂 Schema 不静默丢约束。

具体字段与模块分工见同目录 `protocol-compat.METHOD.md`。

本地自动验证由 Agent 完成。真实服务与宿主认证尚未验证；不因假端点测试通过就宣称真实三服务验收通过。
